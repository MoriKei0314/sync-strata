## 見つけた不安定さ（重大度順）
1. **エンジン単独死からの自動復旧の欠落（旧スタータ）** — 解消済み（次節）。
- strata.exe を kill すると、API フロント（server.py）は生き残り `/v1/models` が HTTP 200 を返し続ける（ただし status は空）。旧スタータのヘルスチェックは HTTP 200 のみだったため、キープアライブは 12:48:34 の実行でも「already healthy」と誤判定し、復旧処理が一切走らなかった。
- 生成リクエストが来るとフロントが遅延再起動する（kill #1: プローブ開始 12:45:53 の 2 秒後にエンジン起動 12:45:55、という傍証あり）が、その間リクエストはハングする（60秒プローブはタイムアウト）。生成リクエストが来なければ、エンジン不在のまま無期限に放置される（kill #2 で 8 分間不在を確認）。
2. **ツール呼び出しが本番 Gateway 経由で発動しない** — 未解消（コード調査領域）。
- toolEvents=0 で、Gateway ログにもツール関連の行が一切ない。直接 Sync API（/v1/chat/completions）へのツール呼び出しは段階移行テストで成立実績があり、接続定義の形（kind=ollama＋/v1）は 27B 時代と同一。Gateway 側のツール提示／応答解析の経路調査が必要で、設定変更では直せないと判断した。
3. **RAM 逼迫とページングの常態化** — 未解消（トレードオフのため意図的に変更せず）。
- Sync の RAM 予算 20GiB＋clef 約 11GB＋WSL/Docker＋常駐アプリで 32GB を使い切っている。予算を下げると decode が大きく落ちる（チューニング実測: 実効予算 13.5GiB で約 35 tok/s、16.25GiB で 58.6 tok/s）ため、速度優先の現行値を維持した。根本解は RAM 増設（64GB 化）で、本テストの範囲外。
4. **短いターンでも平均約50秒の応答時間** — 構造的性質。
- 内訳の目安: エンジンの固定オーバーヘッド約10秒＋prefill（新規セッションでも入力約 2,100 トークン。最終確認ターンの usage 実測）＋unpin 時の判定＋フィード判定との CPU 競合。pin/unpin の差がほぼなかったことから、単独要因ではなく合算。
5. **判定 clef の恒常的な重さ** — 構造的性質。
- clef-flash は Modelfile で num_gpu 0（CPU 推論）。専用ランナーは GPU サポートなしでビルドされており、Ollama も「AMD ドライバが古く ROCm 推論不可」と警告する（Vulkan 経路もこのモデルでは使われない）。スレッド数は物理コア 8 で既定最適。フィードの翻訳/要約判定が窓内 n=90 と頻繁で、ユーザーturnの判定と CPU を取り合う。
6. **並行ターンの直列化**: 2並行で各約150秒。エンジン単一キューの想定内の挙動だが、複数セッション同時利用時の体感は悪化する。
7. **自動抽出の発火タイミングのばらつき**: 経路は正常だが、セッションA分はターン終了から17分＋90秒時点でも未生成だった（セッションB分は自動生成済み）。ウォーターマーク／スケジュールの仕様とみられる。
8. **never rang の新規発生なし**: バッテリー全ターン＋キルテストに伴うエンジン再起動2回を通して発生なし。累計1件は今朝の自動起動直後の初回リクエスト分のみ（チューニング時と同じパターン）。
9. **Gateway 起動直後の vault 再検証によるセッション作成タイムアウト**は今回再現しなかった（セッション作成は全て即時 201）。

## 解消した不安定さ（#1: エンジン単独死の復旧）
### 変更内容
- **スタータ v3.1**（`C:\Users\kesui\bantoh-sync-start.ps1`、SHA256 `EA4F9E9794540C4D33665EC9D9B0A7541DB75FED34D6F19205BD1EFB3E43B4B8`）:
- ヘルス判定を「HTTP 200 **かつ** モデル status.value == loaded」に強化。
- state が responding-not-loaded の間は最大300秒のグレースで自己回復を待つ（生成リクエスト駆動の遅延再起動＋数分のリロードを妨げない）。ただし **エンジンプロセス不在が90秒続いたら早期介入**（再起動はリクエスト駆動のため、不在＝リロード中でない）、フロント自体が落ちたら即介入。
- 介入時は `sync down --all` で残存スタックを落とし（ポート解放を実測確認）、必要なら SyncStrata アプリプロセスを targeted に停止してから、最速構成で再起動し loaded まで監視する。
- **キープアライブ間隔の短縮**: タスク `bantoh-sync-autostart` の繰り返しを PT10M → **PT3M**（検出遅延の短縮）。

## 解消できなかったものと理由
- #2 ツール呼び出し: Gateway 本体のツール提示／解析経路の問題とみられ、設定・環境変数・タスクの範囲では直せない。切り分け材料（toolEvents=0、関連ログなし、直接 API では成立、接続定義は 27B 時代と同形）は本書に残した。
- #3 RAM 逼迫: Sync の予算削減は decode 速度の大幅低下と引き換えで、ユーザーが求めた最速構成を損なうため実施せず。解消には RAM 増設が要る。
- #4 応答時間・#5 判定の重さ・#6 並行直列化: エンジンと clef ランナーの構造的性質（CPU 推論、単一キュー、固定オーバーヘッド）で、設定ノブの範囲に効くものがなかった。
- #7 抽出タイミング: 経路自体は正常（自動生成の実績あり）で、タイミングのみの話のため対象外とした。
