# 宿題解決レポート — ツール呼び出し／RAM／速度（2026-11-22）

Sync 一本化後の多角テスト（post-migration-test.md）で残った宿題3件への回答。
結論を先に: **宿題1（ツール呼び出し）は製品バグではなく、こちらのテストドライバの不備だった**（本番 Gateway 経由でツール発動を実証済み）。宿題2（RAM）は予算を絞っても空きの「底」が改善しないことを実測し、現行構成を維持。宿題3（速度）は clef 判定が構造要因であることを本番ログの全数集計で再確認した。

## 宿題1: 本番 Gateway 経由で Sync のツール呼び出しが発動しない

### 特定した原因: テストドライバが `tools: true` を送っていなかった

- 前回テストのドライバ（pm-driver.py）は、プライバシーターンにだけ `"tools": true` を付け、**ツール確認ターン（セッション bf3f7669）には付けていなかった**。
- Gateway のツールループは `POST /api/chat` の `body.tools === true` のときだけ動く設計（`apps/gateway/src/server.ts`、約1967行）。ツール提示はネイティブ function calling ではなく、システムプロンプト末尾へツール一覧と呼び出し形式（```tool フェンス）を文章で足し、応答テキストから `parseToolCall`（`apps/gateway/src/tool-protocol.ts`）で解析するテキストプロトコル方式。プロバイダ（OpenAI 互換／Ollama 互換とも）へは tools フィールド自体を送らない。よって **kind=ollama かどうかはツール可否に無関係**で、当初疑った「Ollama ネイティブ形式前提の提示／解析の不一致」は存在しなかった。
- 本番ログの裏付け: 失敗ターンの turn.start は `"tools":false`。全ログで tools:true の turn.start は333件あり、Sync へルーティングされたものは0件（全てクラウド接続へ行き、大半が toolEvents≥1 を記録）。つまり「Sync でだけ発動しない」のではなく「Sync へ tools:true で頼んだことが一度もなかった」。
- UI 側の前提: チャット画面のツール有効化はユーザー側トグル（localStorage `bantoh.toolsEnabled`、既定 OFF）。API 利用時に tools:true を送るのはクライアントの役割。

### 実施したこと

1. **本番実証**（コード変更なしで発動を確認）: 本番 Gateway へ tools:true＋Sync ピンで「vault のルートの一覧をツールで確認して」と依頼（セッション efff815e、2026-11-22 04:47 UTC）。`file.list` が status=executed で発火し（durationMs 63）、結果の実データ（memory/、B.A.N.T.O.H/ 等）が応答本文に反映された。所要57.3秒。
2. **穴だったテストカバレッジを追加**: 実プロバイダ経路（createChatProvider→OpenAI互換）で「ツール用システムプロンプトがローカル接続のシステム統合（systemPolicy＋clef 状態行）を経ても末尾に残ること」「tool フェンスが chat／chatStream の両方で無変形に届くこと」を固定する新規テスト `packages/providers/test/local-tool-turn.test.ts`（4テスト）を追加。既存テストはスタブルーター経由か system 統合の一般論のみで、この実経路は未カバーだった。
3. **テスト結果**: 新規4/4通過。全スイート 1530/1531 通過。失敗1件は `codex-cli.test.ts` のハング検出タイミングテストで、単独実行2回とも通過する無関係な flaky と切り分け済み。
4. **反映**: B.A.N.T.O.H. main へ push（新 head `07c4251ec43de5d5ef16d05137c47c19aa2a8d08`、変更は新規テストファイル1件のみ）。母艦 Gateway は bantoh-restart.ps1 で反映し EXPECTED_HEAD_OK／SMOKE_OK、チェックアウト HEAD=07c4251 を確認。UI 変更なし（APK 対象外）。

## 宿題2: RAM 逼迫（予算 20GiB／PIN 14 の見直し）

同一ベンチ（短文×3＋decode 1000tok×2＋長文2500tok、Sync 直接）＋OS サンプラ（15秒間隔）で2構成を実測比較した。

| 指標（ベンチ時間窓） | A: 現行 20GiB／PIN 14 | B: 候補 18GiB／PIN 12 |
|---|---|---|
| decode tok/s（1000×2＋2500 の3本） | 46.2 / 50.0 / 49.0（別ラン: 41.3 / 44.1 / 43.1） | 42.4 / 42.1 / 45.1 |
| 空き RAM 平均 | 1.06 GB | 1.73 GB |
| 空き RAM 最小 | 0.94 GB | 0.66 GB |
| ページファイル使用 | 12.3〜12.6 GB | 10.4〜11.2 GB |
| コミット最大 | 78.2 GB | 75.1 GB |

- **判定: B は不採用、現行 A を維持**。平均空きとページファイルは改善するが、安定性の決め手である「負荷時の空きの底」が上がらない（むしろ低いランが出た）。decode は横ばい〜やや低下。エンジンには elastic RAM（空きが1GBを割ると自動で専門家コピーを返却）が既にあり、枠を絞っても底は clef（約11GB）や WSL／Docker 等の他消費者で決まる、という実測と整合する。過去実測（実効13.5GiB→約35 tok/s）からも、これ以上の削減は速度を確実に悪化させる。
- 反映: 本番スタータ `C:\Users\kesui\bantoh-sync-start.ps1` と切替スクリプト `D:\SyncStrata-trial\switch\Start-SyncMode.ps1` は両方とも既に 20／14 で一致しており、**変更なし**（不採用のためバックアップ作成も不要だった）。ベンチ後に本番構成（20／14）で正規起動し直し、loaded と自動起動タスク（bantoh-sync-autostart、再有効化済み・Ready）を確認。
- 作業中の注意点（再確認）: Sync の起動はタスクスケジューラ経由でないと SSH セッション終了時にスタックごと落ちる（ホルダー問題）。今回も SSH 直起動の構成Bがセッション終了で落ちたため、ベンチ起動は使い捨てタスク経由に切り替えて実施した。

### RAM 根本解（増設）の現実的な選択肢（購入はしていない）

- 現行: DDR5-5600 16GB×2（CFD Sales W5U5600CS-16G、スロット2/4使用）。マザーボード ASUSTeK PRIME B650-PLUS は4スロット・最大128GB。
- 64GB 化の方法は2つ: ①同型 16GB×2 を空きスロットへ追加（最安・現行と同一仕様で相性リスク小）②16GB×2 を 32GB×2 へ差し替え（スロットを空けられ将来128GBへの道が残るが割高）。逼迫の主因が Sync 予算＋clef で計約31GB規模である以上、64GB 化すれば空きの底は10GB超まで上がる見込み。

## 宿題3: 短文でも平均約50秒／clef 判定の重さ

- 本番ログ全数集計（judge.done n=1045）: clef 判定は平均18.8秒・中央値16.1秒・p90 30.0秒・最大95.2秒。ローカル判定への短絡（localJudge）は84件のみ。大半はフィード取り込み側の判定で、チャットの体感（約50秒＝固定待ち約10秒＋prefill＋判定）はこの分布と整合する。
- clef-flash は Ollama の Modelfile で `num_gpu 0`（CPU 推論）指定が恒常構成であり、**設定で削れる余地はない**と実測つきで結論する。判定そのものの呼び出し条件は Gateway の設計（機密性・複雑さの振り分け）であり、無効化は振り分け品質の低下と引き換えになるため行わない。
- Sync 側の decode は本番常駐状態で約43〜49 tok/s（チューニング時の58.6は他常駐なし条件）。短文応答自体は1〜3秒で返っており、体感の主因は生成速度ではない。

## まとめ

- 宿題1は「製品の不具合」ではなく「テスト側がツールを有効化していなかった」ことが原因で、本番実証により解消を確認した。あわせて実プロバイダ経路のテストカバレッジを追加し、B.A.N.T.O.H. main `07c4251` として反映済み。前回の多角テスト報告にあった「Sync 接続ではツールが発動しない」という結論は、本レポートをもって訂正する。

- 宿題3は clef 判定（CPU 推論、平均18.8秒）が構造要因であり設定では削れないことを本番ログ全数で再確認した。
