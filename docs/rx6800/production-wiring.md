### max_tokens 下限の調査結果
- `ConnectionConfig`（packages/core/src/types.ts）に、接続単位の出力トークン下限・上限フィールドは **存在しない**。
- ルーターにはローカル候補向けの「上限」のみがある: `localMaxOutputTokens`（既定 2048）／`localLightMaxOutputTokens`（既定 1024）。環境変数 BANTOH_LOCAL_MAX_OUTPUT_TOKENS 等で変更できるが、呼び出し側の指定（記憶抽出は EXTRACTION_MAX_OUTPUT_TOKENS=1024 で固定）とは min を取るため、**下限としては機能しない**。
- 結論: 下限（最低800〜2500）を設定だけで強制する機構はない。必要ならコード変更（接続スキーマへの下限フィールド追加＋ルーターでの max 化）が要る。今回は本番コードを無断で改変せず、ここに記録するに留めた。
- 実害の切り分け: 本番実経路では、Sync が単独ローカル候補のとき通常ターンに上限は付かず、抽出は 1024 でも disableThinking が chat_template_kwargs として Sync に届き、提案生成まで成功した（残件3）。両ローカル同時稼働時に軽タスク上限が推論を食うケースは、27B と Sync が同時稼働不可のため現行運用では発生しない。

## 残件3: 実経路テスト（2026-11-22 01:15〜01:37）
### 1回目の失敗と対処（切り分け記録）
- 1回目の切替では Sync が起動確認（01:18:33、/v1/models 200）の直後に終了し、ピン留めターンは chatgpt へ流れ、privacy ターンと抽出は「ローカルモデル利用不可」で失敗した。
- 切り分け:
  - Ollama のトレイアプリ（2026-11-21 のユーザー・ログインで起動）が serve を自動再起動する構成で、Start で止めた直後に 11434 が復活していた。さらに Gateway の判定呼び出しで Ollama 内蔵ランナー（llama-server.exe、ワーキングセット約10.7GB、ポート 54289）が立ち、RAM を圧迫した。なおこの llama-server.exe は 27B 本体ではない（27B は正しく停止していた。watchdog も無効化済みで、27B の再起動は起きていない）。

- max_tokens 下限はコード変更が必要（上記）。現行運用では実害なしと切り分け済み。
- テスト用セッション2件（失敗回 3cc734dc-…、成功回 756b4b7b-…）と、ダミー事実の提案3件が本番側に残っている。提案はユーザーの判断待ち（却下想定）。
- 「27B を切って Sync 一本」への判断材料（会話・機密・抽出の3経路の本番実証）はこれで揃った。移行そのものの実施はユーザーの判断に委ねる。
